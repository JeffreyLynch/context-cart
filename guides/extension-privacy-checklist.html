How to Check What a Chrome Extension Really Does With Your Data

Last updated: June 11, 2026 · A practical checklist anyone can follow

Browser extensions run inside the most sensitive software you own. The past couple of years have made the stakes obvious: popular extensions with hundreds of thousands of users have been caught quietly harvesting browsing history for resale, established extensions have been sold to new owners who shipped tracking code in a routine update, and "free" tools have monetized by injecting affiliate codes or relaying user data to analytics brokers. Store review catches some of this. It does not catch all of it, and it can't catch a behavior change that ships after approval.

The good news: you don't have to take any extension's word for it — including ours. Chrome gives you the tools to verify what an extension actually does. Here is the checklist, in order of effort.

1. Read the permissions like a skeptic (2 minutes)

Before installing, the store listing shows what the extension can do. After installing, check chrome://extensions → Details → "Site access" and "Permissions."

  • The single biggest red flag is "Read and change all your data on all websites" (host access to <all_urls>). Some tools genuinely need it (ad blockers, password managers). Most don't. Ask: does this extension's stated job require seeing every page I visit?
  • Prefer extensions built on activeTab — it grants access only to the current tab, only when you explicitly invoke the extension, and the access ends when you leave the page. It cannot watch you browse.
  • Optional permissions are a good sign. Well-behaved extensions request sensitive access only when you enable the feature that needs it, and drop it when you turn the feature off.
  • Watch for permission creep in updates. Chrome disables an extension and asks again when an update demands broader access — never click through that prompt on autopilot.
  • Mismatch test: a "color picker" wanting your browsing history, a "PDF converter" wanting webRequest on all sites — if the permission doesn't map to a visible feature, assume it maps to a business model.

2. Watch the network traffic yourself (10 minutes)

This is the decisive test, because network traffic doesn't lie. An extension that exfiltrates data has to make requests, and you can see every one of them.

  1. Go to chrome://extensions, enable Developer mode (top right).
  2. On the extension's card, click the link under "Inspect views" — usually "service worker". A DevTools window opens attached to the extension's background process.
  3. Open the Network tab in that DevTools window and leave it open.
  4. Now use the extension normally for a few minutes: click its icon, trigger its features, browse some pages.
  5. Every request the background process makes appears in that list. Look at the destination domains. Requests to the developer's own API may be legitimate (sync, accounts); requests to analytics domains, ad networks, URL-shortener-style hosts, or anything you can't explain deserve hard questions.

Also check the extension's visible pages: if it has a popup or side panel, right-click inside it → Inspect → Network tab. And remember that content scripts (code injected into web pages) make requests that show up in the page's DevTools, attributable in the "Initiator" column.

One run proves the extension was quiet today. Telemetry is often batched or delayed, so repeat the check occasionally — especially after updates.

3. Inspect the actual source code (30 minutes, no coding required for the basics)

Every installed extension's code is already on your disk, and MV3 forbids remotely-loaded code, so what you see is what runs.

  • Easiest path: use the free "extension source viewer" tooling or download the CRX and unzip it; or find the extension's folder under your Chrome profile's Extensions directory.
  • Start with manifest.json. It declares every permission, every host the extension can touch, and every script it runs. Five minutes with the manifest tells you more than any marketing page.
  • Search the code for network calls: grep for fetch(, XMLHttpRequest, navigator.sendBeacon, and http. A privacy-respecting utility extension will have few or none; each hit should have an obvious, user-initiated purpose.
  • Beware heavy obfuscation. Minification is normal; deliberately scrambled logic in a simple utility is a red flag in itself. The Chrome Web Store policy requires submitted code to be reviewable.
  • Open source is the strongest version of this — when the repo is public you can read the code in comfort and check that the published version matches it.

4. Read the data-safety disclosure — critically (3 minutes)

Chrome Web Store listings include a "Privacy practices" section where developers must declare what data they collect and certify limited use. Read it, but read it correctly:

  • It's a self-declaration, spot-checked rather than verified line-by-line. Treat it as a claim to be tested with steps 1–3, not as a guarantee.
  • "Does not collect data" is a strong, falsifiable statement — a developer lying there risks removal, so it carries real weight. Vague categories ("user activity," "website content") deserve follow-up: collected when? sent where?
  • Click through to the linked privacy policy. A good one names the exact permissions, explains each, and tells you every path data can take out of the extension. A bad one is a generic template that never mentions the extension's actual features.
  • Check the developer's contact info and history. An anonymous developer with one extension and no website is a different risk profile from an identifiable person with a public repo.

5. Ongoing hygiene

  • Audit your installed list quarterly and remove what you don't use — every extension is attack surface, and abandoned ones get sold.
  • Be suspicious of ownership changes. If an extension's developer name or privacy policy suddenly changes, re-run this checklist.
  • Fewer, more-scrutinized extensions beat many casual ones.

The standard worth demanding

The strongest privacy claim an extension can make is also the easiest to verify: zero network calls. If an extension's background process makes no requests at all, there is no way for your data to leave — no policy fine print required, and step 2 above proves it in ten minutes.

That's the standard we hold our own work to: Context Cart, the snippet-collecting extension this site belongs to, stores everything in local browser storage, uses activeTab plus optional, removable host access instead of all-sites access, and makes zero network requests of its own — open DevTools on its service worker and watch. Whatever extension you're evaluating, ask whether it can pass the same test.
